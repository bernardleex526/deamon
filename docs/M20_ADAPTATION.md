## 1. 部署结论

**点云转扫描节点和 M20 速度桥部署在 GOS；官方 SLAM 建图仍在 NOS 运行。**

| 主机 | 文档默认地址 | 原厂职责 | 本次部署决定 |
| --- | --- | --- | --- |
| AOS | 10.21.31.103 | basic_server 接收上层指令，rl_deploy 执行强化学习运控、步态与关节控制，另有 MCU/感知相关服务 | 只通过公开接口通信，不安装算法，不修改运控 |
| NOS | 10.21.31.106 | 雷达驱动、定位、规划、避障、充电及 PTP Master | 运行 `drmap mapping` 完成官方 SLAM 建图；保留原厂传感器链路 |
| GOS | 10.21.31.104 | 用户二次开发主机，接收并处理转发来的雷达原始组播 | 安装本仓库；建图期间仅运行被动点云观察器，非建图时才可运行跟随/桥接 |

计算平台文档给出三者均为 RK3588，8 核、16 GB RAM、128 GB eMMC。
用户程序明确要求优先放 GOS，NOS 次之，避免占用 AOS/NOS 核心资源。
GOS 可在测量负载后使用 `taskset -c 4-7`，关闭 OpenCV 窗口，先用单线程点云转换。
这只是资源分配建议，尚没有 M20 实测的 CPU、内存、延迟和温度数据。

## 2. 雷达究竟来自哪里

必须区分物理雷达、原始 UDP 接收/转发，以及 ROS 话题发布者。

- 前雷达地址 `10.21.33.201`，后雷达 `10.21.33.202`；双 96 线，文档量程 0.2~60 m。
- 系统架构将 `rslidar_node` 归于 NOS，负责前后雷达 UDP 接收及约 10 Hz 合并点云。
- 激光雷达专页进一步说明 AOS/NOS 都能通过各自原厂驱动获取点云，驱动配置是每主机独立的。
- GOS 的通路依赖 `multicast-relay.service` 把原始组播转发至 31 网段；GOS 已有厂商解码处理，因此可直接订阅 `/LIDAR/POINTS`。
- 所以不能把 GOS 收到点云简单解释为“ROS 自动从 NOS 转发”：转发层是原始雷达组播，GOS 也存在原厂解析环节。具体本机发布者用现场 `ros2 topic info -v` 核实。
- V1.1.7 起支持 GOS 点云和组播转发，转发服务出厂默认关闭。文档没有在启用命令旁明确写主机名，现场先在 NOS/GOS 检查服务文件及网卡配置，确认跨 33/31 网段的转发服务所在主机后再启用，不能凭名称在 GOS 新建同名服务。

默认 `send_separately: false`，`/LIDAR/POINTS` 是合并的 `sensor_msgs/msg/PointCloud2`。
独立模式把前后点云分到 `/LIDAR/POINTS` 和 `/LIDAR/POINTS2`，可能使原厂导航/定位不可用。
本适配要求合并模式，**不修改厂商雷达驱动配置，也不另起一套 GOS 雷达驱动争抢端口**。

### 坐标的关键例外

专页明确：合并点云已经转换到 `base_link` 物理坐标，但 `dds_frame_id` 配置仍可为 `lidar_link`。
因此本配置令 pointcloud_to_laserscan 的 `target_frame` 为空，保留头部标签与时间戳，不再次 TF 变换。
桥默认检查标签为 `lidar_link`。若实际固件标签是 `base_link`，确认物理坐标后修改 `scan_frame`；
不要为了“标签看起来正确”额外平移 ±0.32028 m。
外接 SDK 的独立原始点云不满足这个前提，不能直接套用本合并点云配置。

## 3. 官方建图与 deamon2 的边界

`jie_deamon` 不是 SLAM、定位、路径规划或地图保存程序，不能替代 NOS 的 `drmap`。
官方建图必须在 NOS 启动：`sudo drmap mapping [-n NAME] [-s] [-b]`，结束时执行
`sudo drmap stop_mapping`。建图时由现场操作者使用原厂遥控器平稳行走。

GOS 只允许使用以下被动入口：

```bash
ros2 launch jie_deamon m20_mapping.launch.py
```

该入口只订阅 `/LIDAR/POINTS` 并发布本地 `/m20/mapping_scan`，不会启动
`robot_nexus`、`m20_bridge`、Web、Android、AOS UDP 或任何速度命令发布者。它不能影响
NOS 的 `/LIDAR/POINTS`、`drmap`、定位、规划或地图激活。

只有在没有运行官方建图、导航、定位或充电任务时，才考虑使用 `m20.launch.py` 的跟随/桥接流程。

## 4. 数据与控制链路

```mermaid
flowchart LR
  F[前后雷达 33 网段] --> N[NOS 原厂雷达链路]
  N --> R[原始雷达组播转发到 31 网段]
  R --> D[GOS 原厂解码和合并]
  D --> P[PointCloud2 /LIDAR/POINTS]
  P --> S[pointcloud_to_laserscan /m20/scan]
  S --> J[jie_deamon 目标跟随]
  J --> V[Twist /m20/cmd_vel_raw]
  V --> B[GOS m20_bridge 20 Hz]
  S --> B
  B -->|UDP 30000 Type 2 Cmd 25| A[AOS basic_server]
  A --> L[AOS rl_deploy 运控]
  A -->|Type 1002 Cmd 6 状态反馈| B
```

这张图表达选定的数据处理通路，不声称 NOS 是所有 ROS 点云订阅者的唯一 DDS 发布者。
`jie_deamon` 是二维扫描目标质心跟随与简单势场避障程序，不是四足底层运控，也不是完整 SLAM/Nav2。
无需用它替换 `rl_deploy`，其 `MODE_NAV` 也不等于 M20 的导航使用模式。

### 为什么选择 DDS 感知 + basic_server 控制

感知通过 ROS 2/Fast DDS 读取标准消息，速度通过 `basic_server` 使用物理单位发送。
不需要复制 `drdds` IDL，也能从 JSON BasicStatus 检查使用模式、运控、步态、充电与急停。
UDP 使用同一个已连接 socket 发送、订阅和接收，保持来源端口不变。每秒发送心跳注册状态上报，
每 50 ms 发一次速度，超过源输入有效期就输出零速度并解除使能。

| 通信 | 地址/话题 | 用途 |
| --- | --- | --- |
| 原厂 ROS 2/DrDDS | `/LIDAR/POINTS` | GOS 本地订阅合并点云 |
| 本地 ROS 2 | `/m20/scan`，`/m20/cmd_vel_raw` | 算法输入与未放行速度 |
| UDP APDU + JSON | AOS `10.21.31.103:30000` | Type=2、Command=25，X/Y 为 m/s，Yaw 为 rad/s |
| 同一 UDP socket | 发送 Type=100/Command=100；接收 Type=1002/Command=6 | 1 Hz 心跳注册；本机已测基础状态约 2 Hz，不主动发送 1002/6 查询 |
| TCP，当前未实现 | AOS `10.21.31.103:30001` | 可用于独立状态管理工具，需按长度处理拆包/粘包 |

`Cmd=21` 是常规/辅助模式的归一化轴指令，不能把本仓库的 m/s 直接塞进去。
`Cmd=25` 及 ROS `/NAV_CMD` 均限定导航使用模式。X 正向前、Y 正向左、Yaw 正向逆时针。

协议采用 `EB 91 EB 90` 同步头、uint16 小端 ASDU 字节长度和报文 ID、JSON 标志 1、7 字节保留，
共 16 字节；后接 UTF-8 JSON `PatrolDevice`。ID 从 0 递增到 65535 后回绕。
JSON Time 使用本地时间字符串，指令/状态超时用单调时钟，避免系统校时使看门狗失效。
零错误 ACK 只说明接收，不代表动作完成；本桥依赖完整 BasicStatus，而不是 ACK 放行。

### ROS `/NAV_CMD` 替代路径

可以用 GOS 向 `drdds/msg/NavCmd` 的 `data.x_vel/y_vel/yaw_vel` 发速度，AOS basic_server 再转交运控。
需原厂消息定义与匹配 RMW，仍要求导航模式、关闭 planner 冲突及充电空闲。
运动专页显示 `MotionInfoValue` 下两个子结构都叫 `data`，不是可直接编译的可靠 IDL 定义；
站立是否自动推进的文字也有矛盾。因此本次不编造兼容包，不假定通用 Twist 能直接替代 `/NAV_CMD`。
拿到对应固件 SDK 后才适合另做纯 DDS 控制后端；目前已实现的 UDP 路径无需该 SDK。

## 5. 已完成的代码适配

1. 新增独立 M20 launch、只读建图观察 launch 和参数集，复用成熟
   `pointcloud_to_laserscan`，不自行写点云解析器。
2. 扫描订阅改为 SensorDataQoS，兼容 best-effort 传感器发布者。
3. 雷达旋转角参数化；原 D1 默认保留 π 旋转，M20 使用 0。
4. 跟随距离、通道宽度和机身排除区域参数化；初始跟随距离 1.2 m，身体参数参考 0.82×0.506 m。
5. 没有命中当前目标时输出零速度，不再追逐上一帧残留目标；当帧计算使用新质心。
6. 直接控制的输入有效期为 0.3 s，定时重发不刷新输入时间。
7. M20 默认关闭 Web、Android 和 D1 动作；不把 D1 的趴下/passive 等字符串映射成 M20 关节断电。
8. 新增独立算法目标话题和跟随使能服务；实际平台还需单独调用 `/m20/arm`。
9. 新增可无 ROS 测试的协议编解码、UDP 客户端、状态门控与扫描检查；默认 dry-run 不创建 socket。
10. 新增合成点云/状态源、Python 测试、C++ 回归测试及 Foxy/Humble CI 定义。

### 放行条件和失败行为

非零输出需要：人工 arm、状态新鲜、RL 状态 17、使用模式 1、正向 Direction=0、
HES=0、Charge=0、Sleep=0、已支持步态、新鲜合法扫描，以及新鲜算法速度。
状态不完整、超时、非有限速度、近障、协议拒绝或 UDP 错误解除使能，恢复数据后不自动重新 arm。
只在解除平台保护后重新人工 arm，才允许新指令通过。

- 指令超时：0.3 s；扫描超时：0.5 s；BasicStatus 超时：1.5 s，适配其 2 Hz 周期。
- 扫描还检查源时间戳，默认拒绝超过 0.5 s 的旧帧、超过 0.1 s 的未来帧、错误 frame 及无有效回波。
- 默认速度上限为 0.3 m/s、0.3 m/s、0.6 rad/s。
- 小于当前步态有效下限的分量置零，绝不为了“动得起来”向上放大。敏捷平地的下限为 0.15/0.25/0.35；标准基础为 0.2/0.35/0.5。因此标准基础在默认 Y 上限下不会侧移。
- 默认矩形停止区域前后各 0.7 m、半宽 0.4 m；桥不做自体点剔除，避免错误遮罩把近障隐藏。自体回波可能使其无法 arm，需实测解决。
- 进程正常退出尝试发送零速度；进程崩溃或网络断开只能依赖机器人端约 500 ms 速度超时保护，必须实机验证。

## 6. 时间、网络与资源

机器人系统为 Ubuntu 20.04 / ROS 2 Foxy / DrDDS（Fast DDS 封装）。GOS 优先使用其原厂环境，
不升级系统 ROS，不覆盖 `/opt/robot`。外部 Humble 可按厂商兼容表联调，但不是“任意 RMW 均兼容”。
`ROS_DOMAIN_ID=0`，外部 ROS 使用 `rmw_fastrtps_cpp`。不要让 `ROS_LOCALHOST_ONLY=1` 阻断跨主机发现。

NOS 是 PTP Master，AOS、GOS、雷达是 Slave；点云戳应与 GOS 系统时钟一致。
需检查原厂 rsdriver 的 ptp=0x1、时间差、GOS 与 NOS 时间同步。
不要把异常扫描改成接收时刻“修好”，那会掩盖延迟。

GOS 与其他主机走机内有线交换机；Wi-Fi 适合界面调试，不作为高带宽雷达链路的首选。
外接电脑在 31 网段接收组播需要路由、网卡、交换机组播配置正确，DDS 发现与雷达原始组播是两种不同通信。
原厂外接指南给出 RSAIRY：前 `224.10.10.201:6691`，后 `224.10.10.202:6692`，示例接收 IP `10.21.31.100`。
这不是完整 SDK 配置；DIFOP、完整外参和双雷达合并需使用官方附件和实际 SDK 校准，不能用只有 roll 的表猜后雷达 yaw。

## 7. 尚不能离线证明的事项

本次完成源码适配和可本地执行的逻辑验证，**不等于已经编译、上机或通过运动验收**。
当前 Windows 没有 ROS/C++ 编译环境、Docker 或已安装的 WSL Linux 发行版，ROS 节点运行与 C++ 测试尚未执行。
CI 文件已提供但没有推送触发，也不能宣称 CI 通过。

机器到手后仍需确认：固件与消息布局、驱动/转发服务所在主机、点云物理坐标与时间戳、
双雷达覆盖及断一路识别、切片高度、动态腿部轮廓、安装偏移、停止距离、最低速度响应、
CPU/延迟、单控制源接管及机器人本体超时停车。
只有一部分有效点也会被判为有效扫描；当前没有双雷达独立健康鉴别或覆盖率诊断。
二维切片也无法保证负障碍、台阶、悬空障碍、玻璃及多目标身份跟踪安全。
原有 APF 仍是原算法，新增门控是保守停止保护，不应解释为已获得完整自主导航能力。
