This record captures bounded, supervised observations on GOS and NOS. It does
not record passwords, enable a live AOS control socket, change factory motion
mode, or claim physical-follow acceptance.

  started for the current boot only.

  healthy in its journal. Driver logs alone were not used as sensor acceptance.

A human stood roughly 1.8-2.0 m in front of the robot. The scan and cloud
inspection produced a candidate near `(x=1.88 m, y=0.03 m)`. In dry-run only,
that target was published once and follow computation was enabled for a bounded
diagnostic, then disabled again.

| Metric | Observation |
| --- | --- |
| Raw velocity samples | 147 nonzero samples while follow was enabled |
| Last raw velocity | about `x=+0.326 m/s`, `y=+0.500 m/s`, `yaw=0` |
| Guarded velocity | zero throughout |
| Bridge arm state | `false` throughout |
| AOS live socket | not opened |
| Post-disable raw output | 125 samples, all zero |

This is only evidence that the selected point can drive the current algorithm.
The lateral component is too large to accept as an expected straight-follow
result. Before any live test, inspect target identity, scan coordinates,
corridor-centering, and APF/obstacle terms; then validate movement, target
loss, occlusion, scan loss, and near-obstacle behavior in dry-run.

## Remaining Acceptance Blockers

1. Identify the source of lateral command generation and show correct X/Y/Yaw
   signs at low speed in dry-run.
2. Demonstrate target identity and loss/occlusion behavior without relying on
   a manually published coordinate alone.
3. Confirm factory navigation, planner, charging, and other velocity owners
   are idle and control ownership is transferred before live startup.
4. Confirm live BasicStatus, actual gait minimums, physical units, remote/hard
   emergency stop, and robot-side timeout behavior.
5. Measure physical stop distance for each software and communication fault.

No physical walking, AOS arm, mode change, gait change, `commissioned=true`,
or live bridge start occurred in this record.
